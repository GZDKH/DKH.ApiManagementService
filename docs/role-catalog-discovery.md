# Shared role catalog: discovery-only refactor

Decision: extend the existing `DKH.Platform.Authorization.PlatformRoles` catalog and integrate its constants into existing consumers. No authorization behavior delta; OpenSpec proposal skipped for a mechanical refactor.

Existing implementation: `src/Security/DKH.Platform.Authorization/DKH/Platform/Authorization/PlatformRoles.cs` owns realm, admin and shopper roles. AdminGateway `Authorization/Permissions.cs` duplicates granular and manager roles; its `AddRolePolicy` registration consumes those codes as Keycloak roles. Staff service has two local role catalogs; Engagement checks its operator role; Storefront service and AdminGateway check purpose-bound theme roles. CounterpartyService uses the merged MR182 policy. Isolated worktree from fresh origin/main; coordinator worktree untouched.

Source evidence: checked-in `infra/DKH.KeyCloak/realm-export/realm-export.json` role names (only the `roles` subsection inspected), existing authorization code and tests; active Platform MRs checked before implementation. Role names with a colon remain roles when consumed as role claims. `McpPermissions` are API-key permissions and `ResourceAccessPermissions` are object-level permissions; neither is added to the role catalog. Policy names, media attachment roles, workspace membership roles, authentication, grant lists, JWT validation and dev/prod settings remain unchanged.

Public compatibility: retain existing PlatformRoles fields and legacy list contents/order. Add domain-grouped constant fields and a read-only inventory `AllRoleCodes`; do not use that inventory as a policy allow-list. Gateway `Permissions` and local staff/theme constants remain source-compatible aliases. The existing release chain published Authorization 2.1.0. This local integration uses that actual registry package restored by the SDK; version and size match GitLab metadata, and local package/DLL SHA256 hashes are recorded separately (registry checksums are unavailable). Existing automated package bumps are preserved; where main still pins 2.0.0, the exact CI-generated 2.1.0 pin is applied locally. No private package fixture is used for these gates.
